# Документация по миграциям

## Назначение

Изменения схемы базы данных управляются через Flyway.

Миграции лежат в директории:

- [src/main/resources/db/migration](../src/main/resources/db/migration)

## Список миграций

### `V1__create_users.sql`

Создает таблицу `users` для аутентификации и авторизации сразу в финальной форме с полем `login`.

### `V2__create_regions.sql`

Создает таблицу `regions` со справочником регионов.

### `V3__create_doctor_profiles.sql`

Создает таблицу `doctor_profiles`, связанную с:

- `users`;
- `regions`.

### `V4__create_patient_profiles.sql`

Создает таблицу `patient_profiles` сразу в финальной форме карточки пациента:

- `patient_code`;
- `birth_date`;
- диагноз;
- характеристики клапана;
- параметры операции;
- медикаменты;
- `created_at`.

### `V5__create_examinations.sql`

Создает таблицу `examinations`, связанную с `patient_profiles`.

### `V6__create_characteristics.sql`

Создает таблицу `characteristics` сразу в финальной форме с полями `code`, `name`, `unit`.

### `V7__create_examination_characteristics.sql`

Создает таблицу `examination_characteristics` в финальной форме без дублирования `unit`.

### `V8__seed_regions.sql`

Заполняет таблицу `regions` справочником регионов.

### `V9__introduce_patient_creation_flow.sql`

Техническая no-op миграция.

Номер сохранен в истории Flyway, но для чистой установки схема создания пациента уже формируется предыдущими базовыми миграциями.

### `V10__finalize_region_based_patient_model.sql`

Фиксирует служебные детали региональной модели доступа:

- добавляет индекс `idx_patient_profiles_region_id` для выборки пациентов по региону;
- документирует бизнес-инвариант, по которому для пациента `users.login` и `patient_profiles.patient_code` должны совпадать;
- фиксирует правило, по которому врач получает список пациентов региона через свой регион, а не через прямое владение карточкой.

### `V11__finalize_characteristics_catalog.sql`

Заполняет каталог характеристик обследований 50 placeholder-значениями с кодами `metric_01` ... `metric_50`.

### `V12__replace_patient_age_with_birth_date.sql`

Техническая no-op миграция.

Номер сохранен в истории Flyway, но для чистой установки `patient_profiles` уже создается с `birth_date`.

## Почему миграции разделены именно так

- Базовые таблицы создаются раньше зависимых сущностей.
- Справочник регионов отделен от структуры таблиц.
- Финальная схема пациента закладывается сразу в базовых миграциях, без обязательных transitional replace-steps.
- Логика обследований отделена от карточки пациента.
- Каталог характеристик наполняется отдельной сидирующей миграцией `V11`.
- `V9` и `V12` сохранены как no-op номера для непрерывной истории версий.

## Текущее состояние

- Все 12 миграций применяются успешно.
- Тесты поднимают PostgreSQL через Testcontainers и проверяют применение миграций.
- Миграции `V9`, `V10`, `V11` и `V12` синхронизированы с текущей backend-реализацией создания пациента и каталога характеристик.
