# Документация по миграциям

## Назначение

Изменения схемы базы данных управляются через Flyway.

Миграции лежат в директории:

- [src/main/resources/db/migration](../src/main/resources/db/migration)

## Список миграций

### `V1__create_users.sql`

Создает таблицу `users` для аутентификации и авторизации.

### `V2__create_regions.sql`

Создает таблицу `regions` со справочником регионов.

### `V3__create_doctor_profiles.sql`

Создает таблицу `doctor_profiles`, связанную с:

- `users`;
- `regions`.

### `V4__create_patient_profiles.sql`

Создает исходную таблицу `patient_profiles`.

### `V5__create_examinations.sql`

Создает таблицу `examinations`, связанную с `patient_profiles`.

### `V6__create_characteristics.sql`

Создает таблицу `characteristics`.

### `V7__create_examination_characteristics.sql`

Создает таблицу `examination_characteristics` со значениями характеристик обследований.

### `V8__seed_regions.sql`

Заполняет таблицу `regions` справочником регионов.

### `V9__introduce_patient_creation_flow.sql`

Фиксирует новую схему для backend-сценария создания пациента врачом:

- переименовывает `users.email` в `users.login`;
- убирает из `patient_profiles` устаревшие персональные поля пациента `birth_date` и `phone`;
- добавляет обезличенный код пациента `patient_code`;
- сохраняет в `patient_profiles` поля ФИО пациента: `last_name`, `first_name`, `middle_name`;
- добавляет медицинские поля карточки пациента;
- фиксирует параметры единственной операции пациента в полях `operation_*`;
- добавляет ограничения на возраст и длительность операции;

Миграция `V9` несовместимо меняет старую модель карточки пациента: убирает прежние персональные поля пациента и переводит логин пользователя из `email` в `login`. Она рассчитана на учебный или заранее подготовленный контур, а не на миграцию legacy-данных пациента без отдельного backfill-сценария.

После `V9` backend поддерживает создание карточки пациента врачом. Логика обследований этой миграцией не меняется.

### `V10__finalize_region_based_patient_model.sql`

Финализирует региональную модель доступа к карточке пациента и ограничения схемы:

- добавляет индекс `idx_patient_profiles_region_id` для выборки пациентов по региону;
- убирает DB-default у `patient_profiles.created_at`, чтобы timestamp контролировался приложением и не имел двойного источника истины;
- документирует бизнес-инвариант, по которому для пациента `users.login` и `patient_profiles.patient_code` должны совпадать;
- фиксирует правило, по которому врач получает список пациентов региона через свой регион, а не через прямое владение карточкой.

### `V11__finalize_characteristics_catalog.sql`

Финализирует каталог характеристик обследований:

- добавляет в `characteristics` поля `code` и `unit`;
- делает `code` и `name` уникальными;
- убирает `unit` из `examination_characteristics`;
- заполняет `characteristics` 50 placeholder-значениями с кодами `metric_01` ... `metric_50`.

## Почему миграции разделены именно так

- Базовые таблицы создаются раньше зависимых сущностей.
- Справочник регионов отделен от структуры таблиц.
- Перестройка модели пациента оформлена отдельной миграцией, чтобы эволюция схемы была прозрачной.
- Логика обследований осталась в прежних миграциях и не зависит от новой карточки пациента.
- Каталог характеристик зафиксирован отдельной миграцией `V11`.

## Текущее состояние

- Все 11 миграций применяются успешно.
- Тесты поднимают PostgreSQL через Testcontainers и проверяют применение миграций.
- Миграции `V9`, `V10` и `V11` синхронизированы с текущей backend-реализацией создания пациента и каталога характеристик.
