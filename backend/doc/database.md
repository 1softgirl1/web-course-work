# Документация по базе данных

## Назначение

Система хранит учетные записи пользователей, профили врачей и карточки пациентов, а также обследования и характеристики обследований.

Текущая версия backend поддерживает сценарий, в котором:

- врач создает карточку пациента;
- пациент получает обезличенный код как username;
- пациент получает временный пароль, который выдается только один раз в ответе на создание карточки;
- карточка пациента относится к региону;
- характеристики обследований заданы фиксированным каталогом из 50 placeholder-значений, у каждой характеристики есть код и фиксированная единица измерения;
- модель обследований остается прежней.

Контроль доступа для этого backend-сценария строится на Spring Security-аутентификации по учетной записи пользователя, проверке роли `DOCTOR` и определении профиля врача по текущей учетной записи. Пациент относится к региону врача, который создает карточку.
Самостоятельная регистрация пациента в текущем backend API не предусмотрена: учетная запись пациента создается только врачом в рамках создания карточки.

## Основные таблицы

### `users`

Хранит учетные записи для входа в систему.

Основные поля:

- `username` — единый идентификатор пользователя для входа;
- `password_hash` — хэш пароля;
- `role` — роль пользователя;
- `status` — состояние учетной записи.

Для врача в поле `username` хранится email.
Для пациента в поле `username` хранится его обезличенный код пациента.

### `doctor_profiles`

Хранит профиль врача:

- ссылку на учетную запись;
- специализацию;
- ФИО;
- регион.

### `patient_profiles`

Хранит карточку пациента, созданную врачом.

Основные поля:

- `user_id` — ссылка на учетную запись пациента;
- `region_id` — регион пациента;
- `last_name`, `first_name`, `middle_name` — ФИО пациента, где `middle_name` остается необязательным;
- `birth_date` — дата рождения пациента;
- `diagnosis` — диагноз;
- `valve_name`, `valve_size`, `valve_material` — характеристики клапана;
- `operation_anesthesia`, `operation_duration_minutes`, `operation_delivery_system` — параметры операции;
- `medications` — список медикаментов, который пока хранится одним текстовым полем;
- `created_at` — дата и время создания карточки.

### `examinations`

Хранит обследования пациента.

### `characteristics`

Хранит справочник характеристик обследований.

Каталог фиксирован, сейчас в нем 50 placeholder-значений. Для каждой характеристики хранятся:

- `code` — стабильный код;
- `name` — отображаемое имя;
- `unit` — фиксированная единица измерения.

### `examination_characteristics`

Хранит значения характеристик в рамках конкретного обследования.

Единица измерения не хранится здесь отдельно: она берется из соответствующей записи справочника `characteristics`.

Использует составной первичный ключ:

- `examination_id`;
- `characteristic_id`.

## Связи между таблицами

- одна запись в `users` может соответствовать одному профилю врача;
- одна запись в `users` может соответствовать одной карточке пациента;
- один регион может содержать много пациентов;
- один пациент может иметь много обследований;
- одно обследование может содержать много значений характеристик;
- одна характеристика может использоваться в разных обследованиях.

## Особенности проектирования

- Данные для входа отделены от профильных данных.
- Username пациента не зависит от персональных данных и строится как обезличенный код.
- Код пациента не дублируется в `patient_profiles`: публичное поле `patientCode` в API берется из `users.username`.
- Прямая связь между пациентом и врачом в модели отсутствует.
- Врач получает доступ к пациентам по совпадению региона врача и пациента.
- Параметры единственной операции пациента хранятся прямо в карточке пациента.
- Медикаменты пока хранятся единым текстовым полем, без отдельного справочника.
- Модель обследований не изменялась и совместима с предыдущими миграциями.

## Auth 2.0

- JWT access token is short-lived and is used in `Authorization: Bearer ...` for protected API calls.
- Refresh token is an opaque multi-session token used by `/auth/refresh` and `/auth/logout`.
- Raw refresh tokens are not stored in the database; only SHA-256 hashes are stored in `refresh_tokens`.
- One user can have multiple active refresh sessions for different devices.
- Refresh rotation revokes the old refresh session and creates a new one.
